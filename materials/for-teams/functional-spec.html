1. System Overview

MediCare Clinic is a web-based clinic management application designed to handle patient registration, appointment scheduling, doctor consultations, and billing. The system serves a Monday–Friday clinic with multiple doctors across various specializations.

Technology Stack

  • Frontend: React single-page application
  • Backend: Node.js REST API with Express
  • Database: SQLite
  • Authentication: JWT (JSON Web Tokens)
  • API Documentation: Swagger UI at /api-docs

Core Modules

ModuleDescription
AuthenticationUser registration, login, profile management
Patient ManagementPatient records, search, medical history
Appointment SchedulingBooking, availability checking, cancellation
Doctor DashboardDaily schedule, consultation notes, prescriptions
BillingInvoice generation, discounts, payment tracking
Admin DashboardSystem statistics, user management, oversight

2. User Roles & Access Control

The system supports three user roles. Each role has specific permissions and should only see data relevant to their function.

RoleCan AccessRestrictions
Patient Own appointments, own profile, booking, billing (own invoices) Cannot view other patients' data. Cannot access admin or doctor dashboards.
Doctor Own daily schedule, patient records (for their patients), consultation notes, medical history Cannot modify patient demographics. Cannot access billing or admin features.
Admin All appointments, patient list (demographics only), doctor management, billing, system statistics Should NOT have access to patient medical history, prescriptions, or clinical notes — those are doctor-only.
Data Privacy Rule: Each role should only see the minimum data necessary for their function. Patient records viewed by admin should exclude medical history and clinical notes. Social Security Numbers (SSN) should be masked or hidden in all views except where explicitly required for billing verification.

3. Authentication & Session Management

3.1 Registration

  • New users register with: first name, last name, valid email address, phone, password, and role
  • Email must be a properly formatted email address (e.g., user@domain.com). Invalid formats like test@ or user@.com must be rejected
  • Passwords must meet minimum complexity requirements
  • Duplicate email addresses must be rejected

3.2 Login

  • Users authenticate with email and password
  • Failed login attempts should return appropriate error messages
Security Requirement: The login endpoint must implement rate limiting to prevent brute-force attacks. After multiple consecutive failed attempts, the system should temporarily block or throttle further login requests from the same source.

3.3 Session Management

  • Sessions are managed via JWT tokens
  • Tokens should expire within a reasonable timeframe (industry standard: 15 minutes to 1 hour for sensitive healthcare data)
  • The system should support token refresh/rotation to maintain active sessions without long-lived tokens
Security Requirement: API responses must never include sensitive credential data such as password hashes, salts, or tokens in profile or user detail endpoints. Only non-sensitive user attributes (name, email, role) should be returned.

4. Patient Management

4.1 Patient List

  • Displays all active patients with: name, email, phone, date of birth, age
  • Age Calculation: The patient's age must be accurately calculated from their date of birth. The calculation should correctly handle edge cases: birthdays that fall today, leap year birthdays (Feb 29), and year boundaries (Dec 31 / Jan 1)
  • Deleted Records: Patients that have been deleted (soft-deleted) must not appear in any listing or search results. Once deleted, records should be completely hidden from all users

4.2 Patient Search

Business Rule: Patient search must be case-insensitive. Searching for "john", "John", or "JOHN" should all return the same results. The search applies to first name and last name fields.
Data Privacy Rule: Search queries should use POST request bodies or secure methods — not URL query parameters. Patient names, SSNs, and other PII must never appear in URLs, as these are recorded in browser history, server access logs, and proxy logs.

4.3 Patient Detail View

  • Shows full patient profile: demographics, contact info, medical history, prescriptions, insurance
  • Access Control: A patient can only view and edit their own record. Changing the patient ID in the URL or API call must not grant access to another patient's data
  • Medical History Visibility: Medical history, prescriptions, and clinical notes should only be visible to:
    • The patient themselves
    • Doctors treating that patient
    Admin/receptionist users should see demographics and contact info but not medical records.

4.4 Patient Deletion

Business Rule: Deleting a patient must be a soft-delete operation. The record is marked as deleted in the database but preserved for audit purposes. However, soft-deleted records must not be accessible via any API endpoint — they should be completely hidden from all queries and direct ID lookups.

5. Appointment Scheduling

5.1 Booking an Appointment

Patients (or admins on behalf of patients) can book appointments by selecting a doctor, date, and available time slot.

Business Rule — Date Restrictions:
  • Appointments can only be scheduled for future dates. Past dates must be blocked/disabled in the date picker and rejected by the server
  • The clinic operates Monday through Friday only. Saturday and Sunday must be disabled in the date picker or clearly indicated as unavailable with an explanation
Business Rule — No Double Booking: A doctor can have only one appointment per time slot. If Doctor A is booked for 10:00 AM on June 1st, no other patient can book Doctor A for 10:00 AM on June 1st. The system must enforce this constraint server-side, even if two users submit simultaneously (race condition protection).

5.2 Available Time Slots

  • Available slots are displayed after selecting a doctor and date
  • The availability endpoint returns time slots that are not occupied by active appointments
  • Cancelled appointments must free their time slots. When an appointment is cancelled, the slot it occupied should become available again for other patients to book

5.3 Appointment List

  • Displays appointments with: date, time slot, patient name, doctor name, status
  • Time Display: All appointment times must display in the user's local timezone, not the server's timezone. Users should see times that match their clock
  • Total Count: The displayed total count of appointments must exactly match the actual number of records. If there are 30 appointments, the UI must show "30" — not an approximation or stale count

5.4 Cancelling an Appointment

  • Patients and admins can cancel scheduled appointments
  • Cancellation changes the status to "cancelled" and frees the time slot (see 5.2)

5.5 Completing an Appointment

  • Doctors can mark appointments as "completed" after the consultation
  • Upon completion, the doctor enters consultation notes and prescription details
  • All text fields in the notes/prescription form must be sanitized before storage and display (see Security section)

6. Doctor Dashboard

The doctor dashboard provides an overview of the doctor's daily schedule.

6.1 Daily View

  • Shows today's appointments by default with option to select other dates
  • Each appointment row displays: time, patient name, contact info, medical history, status, notes
  • Summary statistics: total appointments, completed, pending

6.2 Consultation Notes

  • Doctor enters free-text notes and prescription when completing an appointment
  • Notes are stored and displayed in subsequent views of the patient record
Security Requirement: All user-entered text (notes, prescriptions, medical history) must be properly sanitized before being rendered in the browser. Raw HTML or JavaScript must never execute when displaying stored text. Use text encoding or a sanitization library — never render user content as raw HTML.
Performance Requirement: The doctor dashboard should load efficiently. Patient details for all appointments should be fetched in a single optimized query (using JOINs), not through individual queries per appointment. The dashboard should respond within 500ms even with 50+ appointments.

7. Billing & Invoicing

7.1 Creating an Invoice

  • Invoices are created for completed appointments
  • Fields: associated appointment, patient, amount, discount percentage
  • The total is calculated as: total = amount × (1 − discount_percentage / 100)
Business Rule — Discount Validation: The discount percentage must be validated to ensure it falls within the range of 0% to 100% (inclusive). The system must reject:
  • Negative values (e.g., −50% would incorrectly increase the total)
  • Values exceeding 100% (e.g., 150% would produce a negative total)
Validation must be enforced both client-side and server-side.

7.2 Invoice List

  • Displays all invoices with: date, patient, doctor, amount, discount, total, payment status
  • Patients see only their own invoices; admin sees all

7.3 Payment

  • Pending invoices can be marked as "paid"
  • Once paid, the invoice status cannot be reverted

8. Admin Dashboard

  • Displays summary statistics: total patients, total doctors, appointment counts by status
  • Shows recent appointments (last 20) with key details
  • Lists all registered doctors with their specializations and fees
Business Rule: The appointment count displayed in the admin dashboard must exactly match the actual number of appointment records returned by the API. Any discrepancy between the displayed count and the actual data is a defect.

9. Security Requirements

As a healthcare application handling sensitive patient data, MediCare Clinic must meet the following security standards:

IDRequirementDetails
SEC-01 Input Sanitization All user inputs must be sanitized before storage and display. No raw HTML or script execution should be possible through any text field in the application.
SEC-02 Access Control (IDOR Prevention) Users must only access resources they own or are authorized for. Changing resource IDs in URLs or API requests must not bypass authorization. Server-side ownership validation is required.
SEC-03 Data Minimization in API Responses API responses must return only the data necessary for the requesting function. List endpoints should not include SSN, insurance numbers, or full medical history. Sensitive fields should be available only through authorized detail endpoints.
SEC-04 Secure Token Management JWT tokens must have short expiration times (≤1 hour). Token refresh mechanisms should be implemented. Tokens must never be logged or exposed in API responses.
SEC-05 Brute-Force Protection Login and authentication endpoints must implement rate limiting. After 5 consecutive failed attempts, the account or IP should be temporarily locked.
SEC-06 Credential Protection Password hashes, salts, and authentication tokens must never appear in any API response, including user profile endpoints.

10. Data Privacy Requirements

MediCare Clinic handles Protected Health Information (PHI) and must comply with healthcare data privacy standards.

IDRequirementDetails
PRV-01 Role-Based Data Access Medical history, clinical notes, and prescriptions should only be visible to treating doctors and the patient. Admin/receptionist staff see demographics only.
PRV-02 SSN Protection Social Security Numbers must be masked (showing only last 4 digits) in all displays. Full SSN should never appear in list views, appointment responses, or URL parameters.
PRV-03 Audit Logging All access to patient records must be logged with: who accessed, when, what record, and what action. This audit trail supports compliance requirements and security investigations.
PRV-04 Data Retention on Deletion Deleted records must be soft-deleted for compliance but completely hidden from all API endpoints, searches, and listings. No deleted record should be retrievable through any user-facing interface.
PRV-05 PII in Transport Personally Identifiable Information (PII) must never appear in URLs, query parameters, or server logs. Use request bodies (POST) for searching or filtering by sensitive fields.

11. Performance Requirements

IDRequirementDetails
PERF-01 Server-Side Pagination All list endpoints must implement server-side pagination. Default page size: 20 records. The API should accept page and limit parameters. Returning all records in a single response is not acceptable.
PERF-02 Efficient Database Queries Endpoints must use optimized queries (JOINs) instead of N+1 patterns. Loading a doctor's daily appointments with patient info should require at most 2 queries, not 1 per appointment.
PERF-03 Caching for Static Data Endpoints returning data that changes infrequently (doctor availability for a given date) should implement caching. Repeated identical requests within a short window should not trigger duplicate database queries.
PERF-04 Database Indexing Frequently queried columns (doctor_id, appointment_date, patient_id, status) must have database indexes. Without indexes, query performance degrades linearly as data grows.

12. Usability Requirements

IDRequirementDetails
UX-01 Loading Indicators All actions that make API calls must show a loading indicator (spinner, disabled button, progress bar). The user must receive visual feedback that their action is being processed.
UX-02 Meaningful Error Messages Error messages must clearly describe what went wrong and, where possible, how to fix it. Generic messages like "Something went wrong" are not acceptable — the error should specify the issue (e.g., "Email address is already registered").
UX-03 Form State Preservation When a form submission fails (validation error, server error), all previously entered data must be preserved. The user should not have to re-enter fields that were already correctly filled.
UX-04 Destructive Action Confirmation All irreversible or destructive actions (delete patient, cancel appointment) must present a confirmation dialog before proceeding. One-click destructive actions are not acceptable.
UX-05 Weekend/Holiday Handling Since the clinic operates Monday–Friday, the date picker for appointments should either disable weekends or display a clear message when a weekend date is selected explaining that the clinic is closed.
